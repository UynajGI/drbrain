## 0. 一页速览（TL;DR）

1. **v1 的问题不是"不好看"，是"看不见关键状态"**：浏览器里无法回答"我的库现在能不能搜、搜的是哪个索引版本、为什么搜不到"。v1 的检索语义停留在重构前（书目 BM25 + llamaindex 开关），而系统实际已变成"canonical 正文 → 三腿检索 → 不可变 generation"。（依据：01-brief D1/D2/D9；本方案 §1.1）
2. **v2 不做推倒重来**：v1 的项目作用域、认证/CSRF、SSE 运行流、报告下载、游标分页、空态规范**全部沿用**；v2 是**把"索引与证据"这一层补进去**，并把运行/会话的语言对齐新架构。（依据：01-brief §3 落差小结）
3. **信息架构从 v1 六页 → v2 七页**：新增「索引与语料」「检索与证据」两个一级页；「插件」从一级导航降级为设置页内的"能力与插件"分区（URL 不变）。
4. **MVP 定义 = "导入之后的完整研究路径"**：索引状态可读 → 三腿证据检索可用 → 问答状态如实呈现 → 文献库/会话/运行可用。重任务（`index build`）以**显式 job** 进入，不做页面直连。
5. **无论优先级都必须修的 3 件事**：① `ask` 未建索引时返回 500（改结构化状态 + 指引）；② 概览/设置把"RAG 是否可用"绑在旧 `llamaindex.enabled` 开关上（改按索引真实就绪度判断）；③ 静态资源无指纹（改版后用户可能 24h 看到旧 CSS）。
6. **五条技术取舍已定**：不引构建步骤、不引图表库、视觉 token 以 mockup 为准、全局检索（Ctrl+K）不进 MVP、不做 i18n。（§4）
7. **不迁 SPA**：与旧契约 §2 的"v2 迁前端框架"相反 —— 在单人本机场景下，无构建/零 CDN/服务端渲染的收益大于 SPA 的收益，且能保住现有 1200+ 行 WebUI 回归测试的语义。（§4.7）

## 1. 用户与场景

### 1.1 目标用户（本期唯一主场景：单人研究者）

| 维度 | 画像 |
| --- | --- |
| 是谁 | 博士生 / 博后 / 独立研究者；一个人管自己的文献库（几十→上万篇 PDF） |
| 在哪用 | 自己的机器，`drbrain webui` 起在 `127.0.0.1`，浏览器 + 终端并排开着 |
| 怎么用科学工具 | 习惯"先看证据再下结论"；对"模型编的东西"高度警惕；需要能引用、能复现 |
| 现在的实际工作方式 | CLI 是唯一完整入口：`ingest` → `index build` → `search`/`ask` → 可选 `graph build/embed/closure` → `reason`/`pipeline`；浏览器只覆盖"配置完成之后"的一段路 |
| 对 WebUI 的期待 | "别让我为了看一眼索引状态就切终端"；"我点进去的每条结论都要能回到原文"；"系统不知道就说不知道" |

**非本期目标用户**：课题组/多用户（要账号、权限、审计、配额——roadmap 的 v2 产品化，见 §5.3）；纯浏览器用户（不装 CLI 的人——首次启动/导入/建索引仍在终端，见 §5.3）。

### 1.2 典型任务流

> 五个核心任务流（TF1–TF5）构成本期 MVP 的验收对象；TF6 是研究者最想要但本期显式推迟的一条（§5.2）。

**TF1 · 把我的 PDF 变成"能搜的库"，并确认它现在能不能搜**
研究者导入了 200 篇论文，跑过一次 `index build`。他想知道：现在能搜吗？搜的是哪个版本？我昨天新入库的 5 篇进去了吗？为什么某个查询什么都搜不到？
→ 今天：必须回终端跑 `index status` / `index verify` 并读懂 JSON/文本报告。
→ v2：浏览器一个页面回答全部问题，并能发起一次索引构建（显式 job）。

**TF2 · 就某主题提问，拿到可核证的答案**
"这批文献里，kagome 平带的关联效应有哪些主流解释？"——他要的是**答案 + 每条结论的出处**；如果库里没有足够证据，他要系统直说，而不是给一段像模像样的胡话。
→ 今天：CLI `ask` 可以，浏览器里要么"未启用"要么 500。
→ v2：提问 → 答案 + 逐条出处 → 点出处跳到原文片段；证据不足时显示"证据不足"状态与下一步建议。

**TF3 · 找原文证据（不要模型替我总结）**
写方法部分时需要原文措辞与页码/段落。他要的是**原始文本片段 + 精确定位**，可以复制进自己的稿子。
→ 今天：CLI `search` 三腿证据行（带 locator/route/generation）；浏览器只有书目 BM25。
→ v2：检索页的"找证据"模式，结果 = 原文片段 + 出处 + 是哪条腿找到的 + 是哪个索引版本。

**TF4 · 跑一次研究闭环并审查产物**
发起一次 autoresearch run，离开页面去做别的事，回来看到：跑到哪一步了、产出了哪些结论、每条结论的证据是什么、能不能下载报告、中断了怎么续。
→ 今天：v1 运行页已有 stepper/SSE/claims/报告，但把"中断"显示成异常，且缺新 loop 的讨论层/队列/预算/审批视图。
→ v2：进度可离开、断线可恢复、结论与证据关联、报告可下载、"中断"表述为可恢复。

**TF5 · 维护文献库并把引用交出去**
找到那篇论文 → 看结构/概念/论证 → 看它引用了谁、被谁引用 → 复制引用或导出（BibTeX/RIS/Markdown/OKF）。
→ 今天：v1 文献库页有列表/检索/详情/大纲，但没有引文关系与导出入口。
→ v2：补齐"查引用 + 导出"这两个动作，让文献库闭环。

**TF6 ·（本期推迟）追踪一个概念/方法的演化**
"flat band 这个概念是怎么演化到今天的？谁是关键节点？哪条分支在衰退？"——对应 `evolve`/`landscape`/`frontier`/`paradigm`。
→ 为什么推迟：它依赖知识图谱分支（`graph build` → `graph embed` → `graph closure`）已建立，且现有接口没有为 UI 准备图谱数据（需新增 service 方法与返回结构），属于"需要新后端能力"的一类，不是"把已有能力搬上界面"。（依据：01-brief §2 #24、§4.2；§5.2 I1）

### 1.3 心智模型：把内部术语翻译成用户语言

> 规则：**面向用户的位置只用人话；精确术语只在"诊断详情"里出现（可复制）**。本项目所有页面文案遵守此表。

| 内部术语 | 给用户的话（界面文案） | 什么时候给精确值 |
| --- | --- | --- |
| generation | **索引版本**（"当前的索引版本：gen-…（9 月 16 日 14:22 发布）"） | 诊断详情/复制按钮 |
| leg（bm25 / vector / tree） | **三种找法**：<br>· 关键词匹配（bm25）= 术语/公式/行话最准<br>· 语义相似（vector）= 换个说法也能找到<br>· 按结构导航（tree）= 先看目录与主题，再读原文 | 检索页每条的来源标记 + 诊断详情 |
| leaf / region | **原文片段**（可直接引用）/ **主题摘要**（系统生成，不能当原文证据） | 证据卡上的类型徽标 |
| ReadReceipt | **已读凭证**：证明这段原文真的被读过（不是模型编的） | 诊断详情 |
| RRF / rerank | 多路结果怎么合并、怎么排序 —— **不进正文**，只在诊断详情 | 诊断详情 |
| profile_id / 部署身份 | **索引配置指纹**（换了 embedding 模型会让旧索引失效） | 索引页诊断详情 |
| frontier_remaining | **本轮未处理完的层级构建量** | 索引页状态区 |
| ingested / indexed / retrievable | **已入库 / 已建索引 / 可检索**（三件事，不是一件事） | 索引页三段状态 |
| abstain 系列状态 | 系统**实话实说**：没找到 / 找到的不够回答 / 某条找法不可用 / 超出了时间预算 | 结果卡上的状态条 + 下一步建议 |
| job | 后台任务（可以离开页面，回来看进度） | 索引页/运行页统一用词 |
| project / workspace | **项目**（一组语料 + 会话）；语料是**引用**不是复制 | 项目切换器 |

## 2. 信息架构

### 2.1 导航结构（v2 七页）

```
侧栏
├── 项目切换器（沿用 v1：project_id ↔ workspace 引用）
├── 概览            /
├── 索引与语料      /index          ← 新增
├── 检索与证据      /search         ← 新增
├── 文献库          /papers
├── 会话            /sessions
├── 研究运行        /runs
└── 设置            /settings       （含"能力与插件"分区，/plugins 直链保留）
```

### 2.2 页面树与一句话定位

| 页面 | URL | 一句话定位 | 主要数据源（v1 service / 需新增） |
| --- | --- | --- | --- |
| 概览 | `/` | **现在是什么状态，我下一步该做什么** | `dashboard()` 扩展（加索引健康度） |
| 索引与语料 | `/index` | **能不能搜、搜的是哪个版本、还差什么** | 需新增 `index_status()` / `index_verify()`（对齐 `index status/verify --json`） |
| 检索与证据 | `/search` | **一个问题，两条路**：要证据（原文片段）或要答案（带出处） | 需新增 `evidence_search()`（对齐 `search --json`）+ 现有 `ask()` 修复 |
| 文献库 | `/papers`、`/papers/{id}` | **我的语料里有什么**，以及每篇的结构/概念/论证/引用 | `papers()` / `paper_detail()` / `paper_outline()`（沿用）；引用与导出需新增 |
| 会话 | `/sessions`、`/sessions/{id}` | **带记忆的连续对话**，以及从对话发起研究 | `sessions()` / `get_session()` / `chat_in_session()` / `session_memory()`（沿用） |
| 研究运行 | `/runs`、`/runs/{id}` | **闭环跑到哪了，产出了什么结论与证据** | `runs()` / `run_detail()` / `run_events_tail()` / `run_claims()` / `experiments()` / `run_report()`（沿用）+ ledger 新表只读（需新增） |
| 设置 | `/settings`、`/plugins` | **模型与检索的配置、密钥与登录安全、能力与插件清单** | `settings_view()` / `availability()`（修）/ `plugin_catalog()`（沿用） |

### 2.3 与 v1 的取舍理由

| 决策 | 对象 | 理由 |
| --- | --- | --- |
| **保留** | 项目切换器、作用域模型、认证/CSRF、SSE 运行流、报告下载、游标分页、空态范式、`labels.py` 状态文案单一来源 | 这些是 v1 最有价值的遗产，且已被 1200+ 行回归测试钉住；v2 的核心工作是补检索与索引，不是重做骨架 |
| **新增** | 「索引与语料」页 | v1 完全没有位置安放"索引是否就绪/是否过期/哪条腿不可用"，导致"为什么搜不到"无法解释（D2/D9） |
| **新增** | 「检索与证据」页 | v1 把两种 search 混为一谈，且没有证据检索入口与 generation/locator 展示位（D1/D3/D5） |
| **降级** | 「插件」从一级导航 → 设置页内「能力与插件」分区（**URL `/plugins` 与页面保留**） | 插件发现/conformance 是开发者与运维向能力，不在研究者主路径上（D8：它现在是"发现 + 单插件探针"，不足以支撑一级导航的位置）；保留 URL 可保住现有测试的语义 |
| **沿用** | 会话页（对话 + 记忆 + 发起运行） | v1 的三层记忆与 run 发起契约仍然成立（D6 只需补"记忆 vs 结论"的语义标注） |
| **补齐** | 运行页的状态语汇 | ledger 新增 proposals/critic_reviews/queue/budget/approvals 与新状态（pause/cancel/manual review/interrupted）（D7/D14） |
| **推迟** | 概念演化/图谱/共现图/评测/审计页 | 需要新的后端数据接口（不是"搬界面"），见 §5.2 |

### 2.4 全局壳层约定（v1 沿用 + v2 增补）

1. **空态必须给"下一步怎么做"**：沿用 v1 做法（空态文案带命令或动作指引）。空库/未建索引/无证据/无插件四类空态文案必须可区分。
2. **状态→色只有一套映射**：沿用 `labels.status_of()` + `_macros.status_badge()`；模板里禁止硬编码颜色词。
3. **错误态三分类**：① 用户输入问题（保留输入 + 指出字段）；② 环境/配置问题（给下一步：去哪配置、跑什么命令）；③ 系统内部错误（可复制的 request id + 重试）。**"没找到"与"出错"必须视觉上分开**。
4. **诊断详情折叠**：正文放用户语言，精确 ID（generation、block_id、char span、profile_id、route）放"诊断详情"折叠区，必须可一键复制。
5. **URL 可直达**：列表条件（q、筛选、游标）与详情页保持 URL 可分享、可刷新、可后退（沿用 v1）。
6. **一屏一个主要动作**：每页只有一个主按钮（索引页=发起构建；检索页=检索/提问；会话页=发送；运行页=下载报告）。

## 3. 功能需求

> 每条格式：**用户动作 → 系统响应 → 成功标准**；末尾 `→ 依据` 指向 01-brief 的落差编号（D#）、能力清单序号（§2 #n）或章节。
> 标 `【必须修复】` 的项与优先级无关，是实现阶段必须处理的缺陷。

### 3.1 概览 `/`（FR-D1 … FR-D4）

**FR-D1 · 一眼看到"能不能搜"**
用户动作：打开首页。
系统响应：首屏第一张卡是**索引健康度**——可检索 / 部分可用 / 不可用（三态之一），附一句话原因（"三条找法都就绪" / "语义检索未就绪：还有 320 个片段没算向量" / "还没有索引，先构建一次"）+ 一个"查看索引详情 →"。
成功标准：用户不打开终端、不读 JSON，就能判断当前能否检索；不可用时能看到具体原因而不是一个红色图标。
→ 依据：D9（首屏 KPI 缺可用性信号）、D2；§4.1「Index status / leg readiness」为一等公民。

**FR-D2 · 下一步引导**
用户动作：打开首页（或任何页面）。
系统响应：当存在阻塞项时（未建索引 / 索引落后于语料 / 上次构建失败 / 索引配置指纹变化），显示**引导卡**："要让新入库的 12 篇可检索，需要重建索引 → 去索引页"；无阻塞时显示统计卡（已入库 / 可检索 / 概念 / 论证）。
成功标准：任何一个"系统不可用"状态，都有一条明确的、可点击的出路；不存在"提示了但没法行动"的死角。
→ 依据：D9、v1 设计契约 §5.1（空/加载/失败三态规范）。

**FR-D3 · 最近活动**
用户动作：打开首页。
系统响应：最近运行（带状态，含"中断"语义）、最近会话，各带"全部 →"。
成功标准：沿用 v1，链路不断（首页 → 运行/会话详情）。
→ 依据：01-brief D14；v1 实现现状。

**FR-D4 · 计数不能骗人**
用户动作：看首页统计。
系统响应：展示的"可检索"数量来自索引的真实就绪度，不是"数据库里有几篇"；两者不一致时明确显示差值（"已入库 210 篇，其中 198 篇可检索"）。
成功标准：用户不会在"有 9932 篇但搜不到东西"时困惑（D9 原文场景）。
→ 依据：D9；能力 §2 #10（ingested / indexed / retrievable 三态分离）。

### 3.2 索引与语料 `/index`（FR-I1 … FR-I6）

**FR-I1 · 三态分明**
用户动作：打开索引页。
系统响应：三段状态并列展示：**已入库 → 已建索引 → 可检索**，每段给数量与一句话解释（"入库=正文已登记；建索引=已进入检索结构；可检索=当前版本能查到"）。
成功标准：用户能指着屏幕回答"我的 12 篇新论文卡在哪一段"。
→ 依据：能力 §2 #10；D2。

**FR-I2 · 每条找法的状态**
用户动作：查看索引页的"三条找法"区。
系统响应：bm25 / vector / tree 各一行：就绪 / 未就绪 / 部分可用 + 原因（原文：`ready + reasons`）+ 关键数字（未处理量、覆盖范围）；**显示的是配置里实际生效的找法**（例如用户配置里 `pageindex`/`raptor` 被折叠成 `tree`，页面如实说明"已合并为按结构导航"）。
成功标准：不假设默认三腿；用户的真实配置与页面显示一致；某条腿退化时用户知道"哪些结果我可能没看到"。
→ 依据：D15（实际生效 route 必须如实显示）、能力 §2 #14/#19；§4.1。

**FR-I3 · 索引版本（generation）可见**
用户动作：查看索引页"当前索引版本"卡。
系统响应：版本号（人话：日期时间 + 短 ID）、发布时间、覆盖的语料范围、是否**落后于语料**（库里已有新内容但本次索引没包含）、配置指纹是否与当前设置一致（不一致 → 提示"索引是用旧配置建的，建议重建"）。
成功标准：任何一次检索结果都能被这个版本号复现；"过期"是明确状态而不是静默。
→ 依据：D2/D5、能力 §2 #19；§4.1「Generation」为一等公民。

**FR-I4 · 索引自检**
用户动作：点"自检"（只读动作）。
系统响应：运行现有的完整性检查，返回逐项结果（版本清单与新鲜度、正文索引、向量积压、片段可达性、上次构建结果），失败项给"这是什么意思 + 下一步"。
成功标准：用户能在浏览器里获得与 `index verify` 等价的信息；失败项不是一串 JSON。
→ 依据：能力 §2 #11；D2。

**FR-I5 · 发起一次索引构建（显式 job）**
用户动作：点"构建索引"→ 确认对话框（说明这会长跑、会占资源、可以离开页面）→ 确认。
系统响应：创建一个**后台任务**，进入"排队中 / 进行中（阶段 + 进度）/ 完成 / 失败（失败在哪个阶段 + 可复制的原因）"；离开页面不中断；**同一 scope 已有活跃任务时不新建、不报错，而是复用既有 job 并返回 `already_running: true`**（互斥判定按"同 scope 是否已有活跃 job"，不引入请求幂等键）；失败后可重试；**不提供取消/停止**（当前 job 模型没有 cancelled 语义，构建线程无法安全中断）。
成功标准：用户不需要守着页面；回到页面能看到结果；失败能自助定位（哪一阶段失败 + 下一步）；**不会出现两个并行构建**；页面上不存在一个点了没反应的"停止"按钮。
→ 依据：能力 §2 #9；§6 交接提示 4（长任务需要 job 语义）；**04 §A1（复用 `tree_build_jobs` + `TreeJobStore`；边界 3"不承诺取消"、边界 4"重复提交判定"）**。

**FR-I6 · 未完成量与真实边界**
用户动作：看索引页状态区。
系统响应：如果层级构建是按批推进的，显示"本轮未处理的构建量"（原文 `frontier_remaining`）与"部分覆盖"的真实状态；不把"部分完成"显示成"全部就绪"。
成功标准："部分可用"是一个被承认的正式状态，不是一个待修复的 bug（10k 语料的层级构建仍是分批进行）。
→ 依据：01-brief §4.3（不要假设"有语料就能搜"）；能力 §2 #18。

### 3.3 检索与证据 `/search`（FR-S1 … FR-S8）

**FR-S1 · 两条路，说清楚区别**
用户动作：打开检索页。
系统响应：页头用一句话解释两条路，默认模式为"找证据"：
· **找证据** = 直接在原文里找片段，不生成答案（快，可引用）
· **要答案** = 先找证据再让模型综合，答案带逐条出处（慢，可能"证据不足"）
成功标准：用户不会把"找文献（书目检索）"与"找证据（原文检索）"混为一谈。
→ 依据：D1（两种 search 的语义分裂）；§6 交接提示 2。

**FR-S2 · 找证据：结果行必须回答四个问题**
用户动作：输入查询 → 检索（可限定某几篇论文 / 追加外部来源）。
系统响应：每行结果给出：① **原文片段**（可展开上下文）；② **出处**：论文标题 + 章节/结构路径 + 精确位置；③ **哪条找法给的**（关键词/语义/结构导航）；④ **索引版本**。分数等信息放诊断详情。
成功标准：用户能把这行结果直接变成一条可引用的证据（复制出处 + 片段）；不出现"只有一段文本、不知道从哪来"的结果。
→ 依据：D3/D5、能力 §2 #12；§4.1「Evidence row」为一等公民。

**FR-S3 · 三种找法的状态如实呈现**
用户动作：查看本次检索的结果区。
系统响应：显示本次实际使用的找法与各自的命中情况；某条找法不可用/退化时明确标注（"语义检索本次不可用：索引未包含向量"），而不是静默少给结果。
成功标准：用户知道"我看到的不是全部可能的证据"。
→ 依据：能力 §2 #12/#19、§6 交接提示 3（degraded 与正常要分开）。

**FR-S4 · 原文片段 vs 主题摘要**
用户动作：查看结果。
系统响应：每条结果标明类型：**原文片段**（可直接引用）/ **主题摘要**（系统生成，不可当原文证据）；主题摘要不能单独作为"证据"呈现。
成功标准：用户引用时不会把模型生成的摘要当成论文原文。
→ 依据：D3、01-brief §4.3（不要把模型生成内容当证据）。

**FR-S5 · 要答案：答案 + 逐条出处**
用户动作：切到"要答案"模式 → 提问。
系统响应：返回 ① 答案正文；② **逐条出处**（可点击跳到原文片段/文献库详情）；③ 本次用了哪些找法/哪个索引版本（诊断可折叠）。
成功标准：答案里每一条实质结论都能点回原文；没有出处支撑的句子要被明确标出来（或不出现在答案里）。
→ 依据：D1/D5、能力 §2 #13。

**FR-S6 ·【必须修复】系统不知道时要说"不知道"**
用户动作：提问，但库里没有足够证据（或检索本身失败）。
系统响应：**不返回 500**，返回结构化状态之一：没找到 / 证据不足 / 检索失败 / 某些来源不可用 / 超出时间预算 / 结果退化（可用但部分腿缺失）；每种状态给一句人话 + 下一步（换关键词 / 建索引 / 加语料 / 稍后重试）。
成功标准：① 未建索引时页面显示"还没有索引 → 去索引页"，**不是 500**；② 六种状态在界面上可区分，且不显示为"系统错误"；③ 现有 `unavailable` 契约与测试语义保持不变。
→ 依据：**D4（本研究必须修复项）**、能力 §2 #13、§6 交接提示 3。**需架构确认**：需 service 层捕获"索引未就绪"异常并把 CLI 已有的状态/hint 字段透出（§7）。

**FR-S7 · 从证据进入下一步**
用户动作：在结果行上点"带着它去会话"或"看这篇文献"。
系统响应：能跳到会话（把该证据作为上下文带入提问）或文献库详情页的对应片段。
成功标准：检索不是终点——用户能从证据走向提问/精读，不需要复制粘贴 ID。
→ 依据：v1 已有"带文献引用进入会话"（设计契约 §5），此处扩展为"带证据"。

**FR-S8 · 大结果集不卡（展示上限，不是命中总数）**
用户动作：宽泛查询（可能命中上千条）。
系统响应：展示**前 N 条**（N 可调，默认 20，**上限 100**），并在结果区明确提示"**仅展示前 N 条**——这是展示上限，不是命中总数"；用户可把 N 提到上限以扩大一次展示范围。
成功标准：任何查询都不会让页面卡住或渲染上千行；用户**不会把"前 20 条"误读成"一共就这 20 条"**。
→ 依据：v1 契约 §5.1 长列表规范；**04 §A2 边界 4（证据检索是单页 top-k，FTS/ANN 不返回 total）与 §7.4**；附录 D3（leader 决议：不追加后端计数需求）。

### 3.4 文献库 `/papers`（FR-L1 … FR-L5）

**FR-L1 · 找文献与浏览**
用户动作：关键词搜索 / 按状态筛选 / 翻页。
系统响应：书目检索（标题/作者/概念/论证）+ 状态筛选 + 游标分页；无结果与无入库两种状态可区分。
成功标准：沿用 v1 并保持 URL 可分享（筛选条件进 URL）。
→ 依据：能力 §2 #5/#6；v1 现状。

**FR-L2 · 一篇论文的结构与内容**
用户动作：打开论文详情。
系统响应：元数据 + **正文大纲**（canonical 优先、旧论文自动兜底）+ 概念 + 论证；大纲节点可展开看原文片段。
成功标准：新入库（无 legacy 文件）与老论文在 UI 上表现一致，用户不会看到"这篇没有内容"。
→ 依据：D3、能力 §2 #1；01-brief §1.3（canonical 优先、legacy 兜底）。

**FR-L3 · 原文定位可复现**
用户动作：从检索结果/大纲跳进详情。
系统响应：定位到对应原文片段（高亮 + 位置信息可复制）；无权限/文件缺失/片段已过期时有明确状态。
成功标准：用户能确认"系统引用的就是这一段"，并能把一个稳定坐标交给别人/交给未来的自己。
→ 依据：D3/D5、v1 契约 §5.1（证据可进入来源文献/章节）。

**FR-L4 · 引文关系（后续迭代，MVP 列为可选）**
用户动作：查看"引用了谁 / 被谁引用 / 共同引用"。
系统响应：只读列表 + 跳转（本地库有的可点进详情，本地没有的标注为"未入库"）。
成功标准：用户能判断一篇论文在引用网络中的位置。
→ 依据：能力 §2 #7。**需架构确认**：service 层无引文方法，需新增（§7）。

**FR-L5 · 把引用交出去**
用户动作：点"导出"。
系统响应：可选 BibTeX / RIS / Markdown（含引用风格）/ OKF 包；单篇或当前筛选结果集。
成功标准：用户能直接从浏览器拿到可粘贴到稿件/文献管理器的结果。
→ 依据：能力 §2 #8。**需架构确认**：service 层无导出方法，需新增（§7）。

### 3.5 会话 `/sessions`（FR-C1 … FR-C4）

**FR-C1 · 连续对话**
用户动作：新建会话 → 提问 → 追问。
系统响应：对话历史持久保存；回答带出处；刷新/重启后可继续。
成功标准：沿用 v1；换机器/重启后会话仍在。
→ 依据：能力 §2 #32；v1 现状。

**FR-C2 · 记忆的来源层级可见**
用户动作：查看会话的"记忆"区。
系统响应：区分**项目记忆（本会话继承）/ 会话记忆 / 运行记忆**，每条标注来源、来源引用与更新时间；可显式"提升到项目"。
成功标准：用户知道系统"记住了什么、为什么记住、这句话是从哪来的"；模型摘要不覆盖原始证据。
→ 依据：D6、v1 契约 §4.1；能力 §2 #32。

**FR-C3 · 从会话发起研究**
用户动作：在会话里输入研究主题 → 发起运行。
系统响应：创建运行并跳转运行详情；重复提交只创建一次（幂等）；失败给出原因。
成功标准：沿用 v1（会话与运行绑定，可追溯）。
→ 依据：能力 §2 #27；v1 现状。

**FR-C4 · "记忆"与"结论"不是一回事**
用户动作：查看会话页与运行页的"结论类"内容。
系统响应：两类对象用不同徽标与分区：**会话记忆**（对话沉淀，可提升、可被后续对话继承）与**研究结论**（运行结算产出，带证据与裁决状态）；同一句话出现在两处时不混淆来源。
成功标准：用户不会把"模型在对话里说过的一句话"当成"经过验证的研究结论"。
→ 依据：D6；§4.6（与"两种结论是否合并"的产品建议一致）。

### 3.6 研究运行 `/runs`（FR-R1 … FR-R6）

**FR-R1 · 发起与幂等**
用户动作：发起运行（选会话、填主题、设定轮次上限）。
系统响应：后台任务 + 立即跳详情；同一次提交重复点击只产生一个运行；主题重复时按既定语义"续跑已存在的运行"而不是静默新建。
成功标准：沿用 v1（幂等键 + 归属校验）。
→ 依据：能力 §2 #27、v1 现状。

**FR-R2 · 进度可离开、断线可恢复**
用户动作：打开运行详情 → 离开页面 → 回来。
系统响应：阶段进度摘要（先给"跑到哪一步 + 当前结论数"，再展开事件与原始 JSON）；实时事件流可断线重连、不重复、不丢内容；断线时显示"连接中断/重连中"且不改变任务状态。
成功标准：沿用 v1 的 SSE 能力（已完成并有测试）；用户看得到"它在动"而不用一直开着页面。
→ 依据：能力 §2 #28/#29、v1 契约 §6.2（已实现）。

**FR-R3 · "中断"是可恢复，不是失败**
用户动作：查看一个被服务重启打断的运行。
系统响应：显示为**已中断（可恢复）**，说明"服务重启导致运行停止；再次发起同一主题会从检查点继续"，并提供去处；不把中断显示成失败、也不把失败显示成"所有节点完成"。

**FR-R4 · 结论与证据**
用户动作：查看运行的结论区。

成功标准：用户能逐条审查研究结论的可信度，不看 JSON。

### 3.7 设置与能力 `/settings`（FR-P1 … FR-P3）

**FR-P1 ·【必须修复】可用性判断按真实就绪度，且两条路分开**
用户动作：打开设置页/首页。
系统响应：`availability` **拆成两个独立条目，各自带 `ready` + `reasons`**，不合并成一个"检索可用"布尔值：

成功标准：在统一存储部署（无 SQL 语料）下不再出现"实际能搜、页面说未启用"的矛盾；**"能找证据但不能要答案"是一个被明确表达的状态**，而不是一个含糊的"检索不可用"。

**FR-P2 · 能力与插件**

成功标准：用户能回答"这个运行能用哪些工具、这些工具从哪来、可信度如何"；不把"已发现"说成"在线"。
→ 依据：D8、能力 §2 #35/#36。

**FR-P3 · 配置与登录安全**
用户动作：查看有效配置（脱敏）/ 重置访问令牌。
系统响应：沿用 v1：脱敏配置 + 来源标注、登录会话列表、令牌轮换（轮换后旧登录态与已有流失效并要求重新登录）。
成功标准：沿用 v1 契约，不因新增页面绕过 CSRF/作用域校验。
→ 依据：v1 契约 §3/§4；能力 §2 #39。

## 4. 技术约束与决策

> 本节回答 `03-frontend-baseline.md` §4.3 的 5 个问题（已获 leader 认可）与 `01-architecture-brief.md` §6.5 的 5 个遗留疑问。

### 4.1 是否引入构建步骤 / 新前端依赖？→ **不引入**

**决策**：保持零构建、零 CDN、vendored htmx、原生 JS + `data-*` 绑定；新增样式进 `app.css`，新增交互沿用 `htmx:afterSwap` 重绑模式。
**理由**：① CSP `default-src 'self'` + `script-src 'self'` 从架构上禁止外链与内联脚本，任何新库都要 vendored 维护；② 现有 3 个静态文件覆盖了全部交互，本次新增的页面主要是**服务端渲染 + 分页 + 轮询**，不需要构建链；③ "`drbrain webui` 开箱即用"是本地工具的核心体验，构建步骤会引入"未构建则不能跑"的失败模式。
**代价与补偿**：必须补 **cache-busting**（baseline P1）——给 `/static/app.css`、`/static/app.js` 加版本指纹（或降为 `no-cache` + ETag）；否则改版后用户可能 24 小时内看到旧样式。**此项列入 MVP 实现清单。**

### 4.2 是否需要图表 / 图谱可视化？→ **MVP 不引图表库；图谱可视化推迟到迭代 1**

**决策**：MVP 的一切"图"用 CSS 条 / 数字 / 内联 SVG 表达（mockup 已证明信息密度够用）；**不引** chart/plotly/d3/echarts/cytoscape。
**理由**：① 本期的数据主要是**计数与状态**（已入库/可检索/未处理量/结论数），不是时间序列分析；② 图谱可视化需要的数据（子图结构、邻居、路径）**后端接口不存在**，属于"新增后端子图查询 + 返回结构设计 + 数据量控制"，不是前端选型问题；③ 引入 vendored 图表库会带来体积、许可证、离线维护三条长期成本。
**升级条件（迭代 1）**：当"概念演化/图谱浏览"立项时，单项决策候选库（必须 vendored、许可证明确、体积可控），并在方案里同时给出后端接口设计。

### 4.3 视觉 token 不一致 → **以 mockup 为准统一**

**决策**：`#1E40AF`（主）/ `#3B82F6`（辅）/ `#D97706`（强调）/ `#F8FAFC`（底）/ `#0F172A`（正文）+ Fira Sans / Fira Code + 6px 圆角。实现版 `--action #2f5fd0` 与 Inter 统一到 mockup 一套。
**理由**：mockup 是本团队的**视觉目标稿**（`design/webui-v1-mockup.html` 已含 28 个 token，可直接抄进 `app.css`），而实现版的色值是当初实现时的偏差，不是决策；两套并存会让"改版到底改成什么样"失去判据。
**退路（不阻塞）**：若前端评估 Fira 系字体自托管（CSP 下不能用 CDN 字体）成本过高，可暂时保留系统字体栈，但**颜色/圆角/间距 token 必须统一为一套**。字体切换不得影响可读性基准（正文 16px / 行高约 1.6）。

### 4.4 顶栏全局检索（Ctrl+K）→ **不进 MVP**

**决策**：本期不做全局检索。入口分工：**找文献** → 文献库页；**找证据/要答案** → 检索与证据页。
**理由**：① 现有 `/api/search` 只覆盖书目实体（papers/concepts/arguments），不覆盖 runs/sessions/plugins，也没有跨实体排序规则——"全局"需要先定义**搜索范围、排序与结果形态**，这是一次独立的产品+后端设计；② 全局检索的价值在被使用频率放大，而本期用户连"证据检索"都还没有入口，先补主路径。
**升级条件（迭代 2）**：当主路径稳定、用户开始抱怨"找运行/找会话要翻页"时立项，范围建议先做"跳转型"（导航到对象）而非"内容型"（检索内容）。

### 4.5 是否补 i18n？→ **不做**

**决策**：保持中文硬编码 + `labels.py` 单一文案表；不引入 i18n 框架。
**理由**：① 现状文案集中在 `labels.py` + 模板，已是"半集中"结构，替换成本可控；② 本期改版要动 IA 与大量新页面文案，同时引入 i18n 会让"文案到底改对没有"的验收复杂化；③ 无多语言用户诉求（单人本机工具，界面中文）。
**代价**：新增页面必须继续**把状态/错误字符串放进 `labels.py`**（而不是散在模板里），为将来 i18n 留出唯一入口——这条作为实现约束。

### 4.6 §6.5 遗留疑问一：service 层 vs CLI `--json` 作为契约面？→ **继续走 service 层，按需扩面**

**建议**：WebUI 继续调用 `app/service.py`（进程内），**不**改成调用 CLI 子进程。UI 需要的字段（索引状态、证据行、自检）通过**新增 service 方法**获得，字段命名对齐 CLI `--json` 的输出契约。
**理由**：① 现有分层（web → service）是硬约束且有测试；② CLI 子进程会引入启动开销、超时、JSON 解析、环境变量依赖与"两个进程同时写库"的风险，而 service 在同一进程内复用连接与配置；③ 字段对齐 `--json` 可以保证"CLI 与 UI 看到的是同一件事"，避免两套语义。
**待办（需架构确认）**：新增 `index_status()` / `index_verify()` / `evidence_search()` 三个只读门面 + 一个 job 提交门面（§7）。**不建议**让 web 层直接调 CLI 或直接读表。

### 4.7 §6.5 遗留疑问二：是否把 tree 腿写进默认 `retrievers` / UI 是否允许改 route？→ **UI 只读；默认值统一交给核心**

**建议**：① UI **只读展示**本次实际生效的找法与状态，不允许在界面上改 route（改配置属于"任意配置编辑"，见 §5.3 非目标）；② 找法默认值目前是**三处不一致**——数据类默认与仓库 `config.yaml` 是两条腿（`["bm25","vector"]`），`config.example.yaml` 是三条腿，本机 `config.local.yaml` 还是旧写法（`["bm25","vector","pageindex","raptor"]`，运行时被折叠为 bm25+vector+tree 并附说明）；这是**配置债**，应由核心统一并在迁移文档里说明，不应把"让用户在 UI 里自己改对"当成解决方案；③ 当检测到旧写法被折叠时，UI 如实说明（"你的配置里 pageindex/raptor 已合并为按结构导航"）。
**理由**：用户视角里"三种找法"是能力不是开关；让用户调检索路数会制造无人能诊断的差异，而"结果为什么不同"会成为支持负担（**已决策 2026-09-16**：本次不改核心默认值、UI 按 FR-I2 如实展示，见附录 C）。

### 4.8 §6.5 遗留疑问三：运行页是否暴露讨论层/队列/审批？→ **本期只读，写动作待权限模型**

**建议**：MVP 展示运行详情的**只读**扩展（消息板、队列与认领状态、预算用量、待人工审核提示）；**不做** approve/claim/驳回等写动作。
**理由**：① 写动作需要权限模型（谁能批准、谁算作者、冲突怎么办）与审计契约，当前是单人本机模式，做写动作的收益低而风险高；② 只读视图已经能回答用户最急的问题——"它为什么停下来了、在等什么"。
**升级条件**：当出现真实的多用户/协作需求，或单人长跑场景下"必须人工介入"变得高频时。

### 4.9 §6.5 遗留疑问四：`ask` 是否流式？→ **MVP 不流式**

**建议**：MVP 的问答是一次性返回 + 加载态（可取消）。
**理由**：① 流式需要新的 SSE 端点与前端拼装逻辑，而本期更关键的是**状态如实呈现**（六种 abstain 状态）——先诚实再流畅；② v1 已有的 SSE 实现是为运行事件设计的轮询式实现，直接复用会把"每秒一帧"的问题带到问答上（baseline P2）。
**升级条件（迭代 3）**：当会话/问答成为高频使用场景且等待感成为抱怨点时，按"复用现有 SSE 生命周期代码"的路径做（不另起一套）。

### 4.10 §6.5 遗留疑问五：memory 与 claims 是否合并为一种"结论"？→ **数据不合并，界面统一分区**

**建议**：不合并数据模型，但在 UI 上统一为「结论」语义的两个分区，用徽标区分：**会话记忆**（对话沉淀、可提升、可继承）与**研究结论**（运行结算产出、带证据与裁决状态）。
**理由**：两者的生命周期、可信度与证据强度不同（一个来自对话，一个来自通过验证的结算）；合并会丢失"这句话到底有多硬"的信息——恰好是研究者最在意的（**已决策 2026-09-16**：维持数据不合并、UI 分区，见附录 C）。

### 4.11 其他实现约束（来自 baseline §4.1，写入实现清单）

1. `app/web/*` 只做 HTTP → service 翻译，**禁止** SQL 与直接 import loop/workflow 内部。
2. 任何非 GET 必须带 CSRF（`X-CSRF-Token` 或表单字段）+ 同源 `Origin`；新增交互沿用 `base.html` 的 `hx-headers`。
3. 错误体双轨（`/api/*` 与 `HX-Request` → JSON；浏览器导航 → 错误页）；URL 里只能传错误码，不能传文案。
4. 列表一律游标分页；不假设全量返回（万篇级语料）。
5. 静态资源加版本指纹（§4.1）。**已落地**：`asset_url()` 内容指纹 + `?v=<fp>`，`base.html` 三处已切换（frontend-dev M8）；约定与边界见 04 §A6 —— **新资源必须过 `asset_url`**，不要改 `StaticFiles` 挂载、不要加配置项。
6. `tests/test_webui.py` + `tests/test_app.py` 必须保持绿；若确需改语义，需同步改测试并在 PR 说明原因。
7. **后台任务统一读法**：运行用 `/api/runs/{id}/…`（保留 v1 SSE），索引构建与 conformance 用 **`GET /api/jobs/{job_id}`**（另有 `GET /api/jobs` 列表，同一套字段 `job_id/kind/scope_key/state/owner/checkpoint/metrics/reason`），由 **htmx 自轮询片段**驱动（1.5–3s，终态自动停）——**不为构建进度引入 SSE**；三种任务共用"怎么读"，但不合并成一张表（04 §A1 结论段）。

## 6. 验收标准

> 每条任务流的验收都是**用户视角可观察**的；括号内为实现方需要提供的证据（截图/测试用例/复现步骤）。

### TF1 · 建库与"能不能搜"体检
- [ ] 从空库状态打开首页，能一眼看到"还没有索引"并**在两次点击内**到达索引页（截图）。
- [ ] 索引页同时显示 **已入库 / 已建索引 / 可检索** 三个数字，且当索引落后于语料时明确标出差值（构造：入库 N 篇 → 建索引 → 再入库 M 篇，页面显示 N+M 入库、N 可检索）。
- [ ] 三条找法的状态与实际配置一致（构造旧写法 `pageindex`/`raptor` 的配置，页面说明其已合并，且不显示为"不可用"）。
- [ ] 索引版本卡显示版本号与发布时间；**篡改/过期场景**（索引后用新配置改 embedding profile）下提示"建议重建"。
- [ ] 点"构建索引"→ 确认 → 离开页面 → 重新打开仍看到进行中/已完成；**重复提交不会产生第二个构建**（自动化测试）。
- [ ] 构建失败时（构造失败阶段）页面显示失败阶段 + 可复制原因 + 下一步命令。
- [ ] 自检结果逐项可读，失败项不显示为原始 JSON 且带"下一步"。

### TF2 · 主题问答（含"系统不知道"）
- [ ] 未建索引时提问 → 页面显示"还没有索引 → 去索引页"，**HTTP 非 5xx**（自动化测试；这是 D4 的验收）。
- [ ] 正常提问 → 答案 + 逐条出处；点出处能跳到原文片段（截图/录屏）。
- [ ] 证据不足场景（库里无关语料）→ 显示"证据不足"状态 + 建议，**不返回 500、不显示编造的答案**。
- [ ] 六种状态（没找到/证据不足/检索失败/来源不可用/超时/结果退化）在界面上可区分（自动化或人工构造）。
- [ ] 会话中提问 → 答案带出处，刷新后历史仍在。

### TF3 · 找证据
- [ ] 结果行包含原文片段 + 论文/章节/精确位置 + 找法标记 + 索引版本（截图）。
- [ ] 每条结果标注"原文片段"或"主题摘要"，摘要不作为证据呈现。
- [ ] 某条找法不可用时明确标注（构造：关闭向量 → 页面显示语义检索不可用）。
- [ ] 按论文限定检索生效（`--paper` 等价的界面操作）。
- [ ] 宽泛查询（≥1000 命中）不卡顿，翻页正常，明确显示"共 N 条"。

### TF4 · 研究闭环
- [ ] 发起运行 → 详情页实时更新阶段与结论数；关闭页面再打开内容不丢（自动化 + 人工）。
- [ ] 断网/断连时显示"重连中"且不改变运行状态；恢复后补齐事件、无重复。
- [ ] 服务重启导致中断的运行显示为**已中断（可恢复）**，并说明如何续跑。
- [ ] 结论区每条结论能点进证据；通过验证的结论与推测明确分开。
- [ ] 报告可下载且包含运行身份、结论、证据引用（文件校验）。

### TF5 · 文献库与引用
- [ ] 新入库论文（无 legacy 文件）与老论文的详情页表现一致，都有大纲与原文片段。
- [ ] 从检索结果跳进详情能定位到对应片段并高亮。
- [ ] 列表筛选条件进 URL（刷新/分享保持）。
- [ ] （若后端到位）导出 BibTeX/RIS/Markdown 可从浏览器完成。

### 全局（所有页面）
- [ ] 1440 / 1024 / 768 / 320 px 下正文无横向滚动；键盘可达；焦点可见（沿用 v1 契约 §5.1 与 WCAG 参考）。
- [ ] 空态/加载/失败三态可区分；"没找到"与"出错"分开；表单错误保留输入。

- [ ] `tests/test_webui.py` + `tests/test_app.py` 保持绿（或同步更新的说明）。
- [ ] 静态资源带版本指纹（或 `no-cache`），改版后不会长时间返回旧文件。
